STV Recap

Single Transferable Voting in Portland

STV elections are widely documented but here is a summary that does two things:

  1. Shows a step by step calculation using R, and

  2. Uses data from an actual Portland election, instead of a toy example. You can validate the results with an actual CVR dataset.

The example uses the 3rd District City Council race from 2024.

Calculating votes from stv ballots.

Voters select from 1 to 6 candidates on their ballots in rank order of preference. Each Portland race listed approximately 30 candidates, and write-ins are allowed. The 2024 city council elections were the first under the new charter reforms, meaning all 12 seats was open and included in the election.

Voters were advised to omit any candidates that they reject outright. Any ranking expresses a willingness to accept a candidate, but the higher the ranking, the stronger the ballot’s effect.

Ballots display a seven column grid; they list all of the candidates and offer ranking slots from 1 to 6. Voters are expected to mark only one candidate per ranking, and to rank them in order from highest to lowest, but ballots are not rejected outright for a single mistake.

We use the term undervote to describe a choice that isn’t marked. If a voter omits a selection for a particular ranking, we have an undervote.

An overvote means more than one candidate is selected for the same ranking.

Three kinds of voter mistakes are relatively frequent. Portland handles them in different ways, none of which leads to an outright rejection.

Mistake #1: Undervotes out of sequence

Some ballots leave some rankings blank within a set of ranked candidates,

t(council_d3_2024[5296,])
         [,1]                
recordID "RCV-0088+10243"    
precinct "55"                
rank_1   "undervote"         
rank_2   "Philippe Knab"     
rank_3   "Cristal Azul Otero"
rank_4   "Rex Burkholder"    
rank_5   "Angelita Morillo"  
rank_6   "undervote"

In this case, Philippe Knab was the voters most preferred choice but the voter marked him in the second ranking. Portland accepts this ballot and compresses the rankings. Knab receives a rank_1, Otero a rank_2, Burholder is rank_3, and Morillo is rank 4. Ranks 5 and 6 become undervotes.

Some jurisdictions are less generous, but Portland will use any information that generates a reasonable inference of the desired ranking.

Mistake #2: Overvotes

A more serious error occurs when a voter assigns the same ranking to multiple candidates. We can’t infer the voters actual preference for those rankings and the ranking must be ignored. The ballot is still accepted for choices with a single correctly stated preference. For example:

Knab would have taken the rank_1 spot on the ballot, even though Bali, Novice, Pham, and Morillo would have been dropped.

The Basic STV Workflow

Once the rankings have been compressed and overvotes eliminated.

Step 1: Determine the number of votes required to win election. For an ordinary race with one winner, the threshold is 50% + 1. For multiple seats, the threshold is lower.

The formula that determines the threshold percentage is: 1 / (1 + number of seats) + 1. For Portland City Council races, this means 25% + 1.

The lower percentage ensures that three winners, and only three winners, will emerge. It also means that diverse representation of minority policy preferenes is more likely.

Use one of the five 8-column data tables provided in the process_cvr_objects.RData file. They are named council_d1_2024, council_d2_2024, council_d3_2024, council_d4_2024, and mayor_2024.

As noted elsewhere, each table has 8 columns, including:

  • recordID and precinct. When combined they uniquely identify each ballot

  • rank_1, rank_2, …., rank_6, containing candidate names

Note that ehe stv() function in the vote package requires a different format, where each candidate is a column and the rankings appear in the body of the data table. The tables with the word “preprocessed” use that format, In this example, I’ll use the eight column format.

We’ll work with the council_d3_2024 table, but you can replace or subset this routine.

Step 9: If there are no winners, eliminate the candidate with the fewest first place votes.

In this example, i take the bottom row of the presorted tally rather than look for the minimum value explicitly. Each system deals with ties differently; in the unlikely event that two or more eliminated candidates are tied, the elimination is chosen arbitrarily here, TBH: I’m not exactly sure how Portland handles that scenario, but I’m sure it’s documented somewhere.

Step 10: Run another round after filtering the eliminating candidate

We execute the compression logic one more time, and repeat until three candidates have crossed the threshold.

A function (or even a recursive function) would make sense at this point.

Almost all of the code shown here is reused…the filtering statement is the only differece.

This code blocks run runs the code above beginning with step 6.

Notice that logically automatically moves a voter’s highest remaining candidate into rank_1. Once all of a voter’s candidates are eliminated, the ballot is considered exhausted.

ballot_data_round_2 <- ballot_data |> 
  
    pivot_longer(cols = !c(recordID, precinct), 
                 names_to = "choice_num", values_to = "choice") |> 
    mutate(choice_num = as.numeric(str_sub(choice_num, -1, -1))) |> 
    
    filter(choice != as.character(eliminated_candidate)) |> 
    
    group_by(recordID, precinct, choice) |> 
      slice_min(choice_num, with_ties = FALSE) |> 
    ungroup() |> 
    
    group_by(recordID, precinct) |> 
      mutate(choice_num = rank(choice_num)) |> 
    ungroup() |> 

    pivot_wider(id_cols = c("recordID", "precinct"),
                names_from = choice_num,
                values_from = choice) |> 
    relocate(recordID, precinct, rank_1 = `1`, rank_2 = `2`, rank_3 = `3`,
           rank_4 = `4`, rank_5 = `5`, rank_6 = `6`)
